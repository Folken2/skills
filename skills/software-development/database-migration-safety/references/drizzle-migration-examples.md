# Drizzle-Specific Migration Examples

Engine/tool-specific mechanics for applying the **database-migration-safety** protocol with Drizzle ORM + Postgres. The parent `SKILL.md` holds the database-agnostic principles; this file is the concrete Drizzle implementation.

---

## Migration File Layout

Drizzle migrations live in `drizzle/migrations/`:

```
drizzle/migrations/
├── 0019_mushy_robin_chapel.sql          # Up migration (generated by Drizzle)
├── 0019_mushy_robin_chapel/             # Migration folder
│   └── down.sql                         # Down migration (YOU create this)
└── meta/
    ├── _journal.json                    # Migration journal
    └── 0019_snapshot.json               # Schema snapshot
```

**Never modify original migration files.** Do not move, rename, or edit `[tag].sql`, and never touch anything in `meta/`. You only ever *create* new `[tag]/down.sql` files.

## Generating the Down Migration

Drizzle generates the up migration but not the reverse. For each statement in `[tag].sql`, write the inverse into `[tag]/down.sql`, in reverse order, grouped by operation type.

### SQL reversal reference

```sql
-- UP: Create table            DOWN:
CREATE TABLE "users" (...);     DROP TABLE IF EXISTS "users";

-- UP: Add column              DOWN:
ALTER TABLE "users" ADD COLUMN "email" text;
ALTER TABLE "users" DROP COLUMN IF EXISTS "email";

-- UP: Rename column           DOWN: rename back
ALTER TABLE "users" RENAME COLUMN "name" TO "full_name";
ALTER TABLE "users" RENAME COLUMN "full_name" TO "name";

-- UP: Change type             DOWN: change back (only if lossless)
ALTER TABLE "users" ALTER COLUMN "age" TYPE integer;
ALTER TABLE "users" ALTER COLUMN "age" TYPE text;   -- WARNING: verify no data loss

-- UP: Create index            DOWN:
CREATE INDEX "idx_users_email" ON "users" ("email");
DROP INDEX IF EXISTS "idx_users_email";

-- UP: Add constraint          DOWN:
ALTER TABLE "users" ADD CONSTRAINT "users_email_unique" UNIQUE ("email");
ALTER TABLE "users" DROP CONSTRAINT IF EXISTS "users_email_unique";

-- UP: Insert data             DOWN: scoped delete
INSERT INTO "users" ("email") VALUES ('admin@example.com');
DELETE FROM "users" WHERE "email" = 'admin@example.com';

-- IRREVERSIBLE — up dropped a table/column:
-- MANUAL INTERVENTION REQUIRED — data permanently deleted, restore from backup.
```

Always use `IF EXISTS` on drops so a partial rollback can re-run. Reverse the last operation first.

### Example down.sql

Given an up migration that creates a `posts` table, two indexes, and adds a `post_count` column to `users`:

```sql
-- Down migration for: 0001_create_posts_table
--
-- WARNINGS:
-- - Dropping "posts" permanently deletes all post data
-- - Dropping "post_count" loses calculated values

-- ===== REVERSE COLUMN OPERATIONS (last first) =====
ALTER TABLE "users" DROP COLUMN IF EXISTS "post_count";

-- ===== REVERSE INDEX OPERATIONS =====
DROP INDEX IF EXISTS "idx_posts_created_at";
DROP INDEX IF EXISTS "idx_posts_user_id";

-- ===== REVERSE TABLE OPERATIONS =====
-- WARNING: permanently deletes all posts data
DROP TABLE IF EXISTS "posts";
```

## Commands

- `npm run db:generate` — generate a migration from the schema diff.
- `npm run db:generate:custom` — empty SQL file for hand-written migrations (RLS, functions, triggers).
- `npm run db:status` — show migration status / identify the current migration.
- `npm run db:migrate` — apply pending migrations.
- `npm run db:rollback` — run the latest `down.sql` and remove its DB record (does **not** clean local files).

> These wrap `drizzle-kit` with `dotenv` (`.env.local` for dev, `.env.prod` for prod). Never call `npx drizzle-kit` directly. A `:prod` suffix targets production — only run it when explicitly instructed.

## Complete Rollback (two phases)

`db:rollback` only reverses the database. A full rollback also cleans local artifacts so the next `db:generate` starts from a correct snapshot.

**Phase 1 — Database rollback** (only if the migration was applied):
1. `npm run db:status` and read `meta/_journal.json` to find the latest entry (`entries[entries.length - 1]`).
2. Confirm `[tag]/down.sql` exists — abort if missing.
3. `npm run db:rollback` to execute `down.sql` and remove the record from `drizzle.__drizzle_migrations`.

**Phase 2 — Local cleanup** (always, with explicit confirmation):
1. Delete `drizzle/migrations/[tag].sql`.
2. Delete the folder `drizzle/migrations/[tag]/` (with its `down.sql`).
3. Delete `drizzle/migrations/meta/[idx]_snapshot.json` (idx zero-padded to 4 digits).
4. Pop the matching entry from `meta/_journal.json` — assert the popped `tag` equals the one you intended before writing the file back.

**Phase 3 — Verify:** re-run `npm run db:status`; confirm the deleted files are gone and the schema is at the prior state.

## Postgres function migrations

`CREATE OR REPLACE FUNCTION` cannot change parameter names or signature — Postgres rejects it. For signature changes: `DROP FUNCTION IF EXISTS name(<exact_type_signature>);` then `CREATE FUNCTION ...`. Use `double precision` (not `float`) and `integer` (not `int`) in the DROP signature. Generate these with `db:generate:custom`.

## Safety notes specific to shared dev DB

- The dev database is shared across worktrees/sessions. `db:migrate` affects everyone at once — announce what you're migrating first, and never run migrations concurrently with another session.
- Drizzle snapshots (`meta/`) can drift; a drifted snapshot makes `db:generate` emit a wrong diff. Resolve drift before trusting generated SQL.
